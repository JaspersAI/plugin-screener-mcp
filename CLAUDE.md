# CLAUDE.md

The `screener-mcp` plugin for Jaspers Terminal, written against `@jaspers-ai/sdk`. The app loads it from a folder in `~/Jaspers/plugins/screener-mcp` (a clone of this repo, or an installed release) and rebuilds it on save. How plugins work, the SDK, and the app's side are in the terminal repo's CLAUDE.md. It runs on the screener MCP server (screener-mcp). The earlier hosted server, with another filter shape and other tools, is plugin-screener's: a separate repo with the id `screener`, whose history up to 3.0.1 this one shares, so the two install side by side.

## Commands

Node 24.

- `npm install`
- `npm run typecheck` — `tsc --noEmit`
- `npm test` — Node's test runner over the `*.test.ts` files, which strips the types itself
- `npm run package` — `build/screener-mcp-<version>.zip`, what a release attaches; the Release workflow runs it on a `v*` tag

Style: square, no rounded corners. Colours are the app's theme variables with the light value as fallback (`var(--jaspers-border, #e5e5e5)`, `var(--jaspers-muted-foreground, #737373)`), so a view follows the app's light and dark; a colour of the plugin's own gets its dark value under `@media (prefers-color-scheme: dark)`. The only colours besides grey are the sign of a number and the verdict of a run.

## The plugin

One connection, `screener-mcp/jaspers`: the screener MCP at `https://s.jsprai.com/mcp` (streamable HTTP, stateless), with `auth: 'oauth'`. The server signs its users in through Jaspers' Account (`https://account.jsprai.com`), which its protected resource metadata names: the terminal, from 0.4.0, connects it on the app's own sign-in with Jaspers and sends that token as a bearer on every call; an earlier terminal runs the OAuth flow itself (Authorize in Settings > Plugins, a sign-in at Account in the browser). There is no secret and nothing in the URL. To run against a server on this machine, point `url` at that server's `PUBLIC_URL` plus `/mcp`; the client refuses a server whose advertised resource is on another origin or path than the URL it was given, so `localhost` and `127.0.0.1` are not interchangeable. `tools` names the five it offers: `screen_companies`, `start_qualitative_screen`, `get_qualitative_screen`, `get_company`, `get_guide`. On it, five sources (`screen`, `guide`, `qualitative-start`, `qualitative`, `company`) and one view. `screen` and `qualitative` have `ttlMs: 0`: a call on a server-side session or a run that is still going is not a function of its arguments, so the app's cache of rows by arguments must not answer for it.

The server owns the fields. `get_guide {topic: "fields"}` answers with one row per field (`field, group, kind, unit, ops, sortable, description`), and the view draws its field picker, its ops, its value inputs, its column picker and its cell formats from those rows. There is no list of fields, labels or units in this repo; a label is made from the field's name (`fieldLabel`).

- `screener.ts` is the pure half, tested in `screener.test.ts`: the state, filter, run and output shapes; `readFields`; `cellText` by unit; `parseValue` and `valueText`, which read what the user types into raw units and back without changing the value ("500M", "$2B", "20" on a fraction is 0.2); `filterText`, `toDraft` and `fromDraft` for the chips and the dialog; `readScreen`, `echoOf`, `inSync` and `screenArgs` for the session; `funnelRows`, `funnelStates` and `removedText` for the funnel; `slug`, `needsStart`, `readStart`, `readRun` for the qualitative stage, and `followArgs`, `mergeRun`, `doingText`, `elapsedText` and `readingAt` for following a run; `evidenceText`, `publishedFilters`, `fitOutput` and `summarize` for what the model reads.
- `ScreenerView.tsx` is the shell: the mount guard (the table mounts once the panel's state is here, so its first run is the right one), one `usePanelState` per key, the screen, the run's start and its polling, the open company's evidence, and what is published.
- `Funnel.tsx` is the funnel (below), `Filters.tsx` the chips and the filter dialog (filters, own tickers, unlisted companies), `Columns.tsx` the column picker, `Table.tsx` the table with a run's verdict columns and the step of a company being read, `Qualitative.tsx` the criteria with the run's buttons and the run's row of the funnel (`RunProgress`), `Evidence.tsx` the open company's answers with their citations, `styles.css` the CSS, `instructions.ts` what the orchestrator is told while the view is focused.

### The session

`screen_companies` keeps the list in a session on the server, and to it a call that names the list (`filters`, `tickers`, `include_unlisted`) is a change of it while one that does not is a read. So `screenArgs` sends the list whole when the session does not hold it yet (the first call, a changed filter) and leaves it out when only the sort, the page or the columns moved; what the session holds is read from the last answer's echo (`applied_filters`, `tickers`, `include_unlisted`). The arguments are made when what is asked for changes, not when an answer lands, so the `session_id` an answer brings is used by the next call and does not cause one. The view writes `state.sessionId`; a session the server no longer has starts a new one. No tickers leave the view unless the user has a list of their own: `tickers` is sent only then, as `[]` only to take back a list the session still holds, and the names a row carries anyway (`cik`, `name`, `ticker`, `tickers`, `sic_description`) are dropped from `columns` before a call.

### The funnel

The view shows the screen as it goes, not only its result: a row for the universe, one for each filter in its turn, and one for the qualitative stage. A filter's row says how many companies it left, how many it removed from those the row before it left, and the first of those by name with the value that did not pass. The server says all of it in the one answer: every call sends `removed_names`, and `applied_filters[]` carries `left` (what passes the filter and every one before it) and `removed` (`ticker, name, value`, the first in the sort order; a company with no value is among them, since no comparison matches it). `matches`, what a filter passes on its own, is the row's tooltip. A server that says neither still gives the first row and the last (`funnelRows`: the first filter leaves what it matches alone, the last what passes all), and no names.

The rows are the state's, so they are drawn before any answer is: `funnelRows` gives each row a key of the universe and the filters up to it, and a row has an answer while the one on screen has the same key there. What a filter left depends on nothing after it, so a filter added at the end leaves the rows above it standing and only the new one waits. The rows of an answer are shown one after another (`ROW_MS` in `Funnel.tsx`, all at once under `prefers-reduced-motion`), so a list narrowed in one call still reads as the narrowing it was; nothing is held back but the funnel's own rows, and the table has the list as soon as it is in. `funnelStates` says which row is at work: the next to be shown, or the first one a call is out for. While a call for another list is out the table's rows are dimmed (`sc-stale`): they are of the list before it.

### The qualitative stage

The orchestrator (or the Run button, which makes the same write) sets `state.criteria` and `state.run = {}`. `needsStart` decides: a `run` with no `id` is the request, and what a model fills in beside it does not count as started, only the server's run id or a failed start with its reason. The view starts the run with `start_qualitative_screen {session_id, criteria}` once the session holds the list on screen (`inSync`) and the server says `qualitative_ready`; over the limit, it writes the reason into `run.error` instead. A latch holds from the call until the run's id is in the state, since a run costs model calls for every company and must not start twice. It then follows the run with `get_qualitative_screen`, without evidence, one call in flight at a time (`followArgs`). The first read is the whole run, at once, so a panel coming back to a run shows where it is. Each one after is `{run_id, wait_seconds: 3, tickers}` with only the companies not yet over, and `mergeRun` brings the run on screen up to date: the server holds a call for its whole wait and tells of each company as it finishes only in progress notices, which do not reach a view, so a long wait is a stale screen; and the app keeps every answer a source gives for good, so the whole run is not asked for again every few seconds. A company's answers are fetched once, when it finishes. While `earnings_calls.status` is `fetching` no company is read, so `tickers` is `[]` and the answer is the counts alone; when the run ends it is read whole once more. The view writes `run.status`. Progress and results stay in the component; `output.qualitative` carries the status, the counts and the earnings-call phase.

Where a run is, is the funnel's last row: what it is doing (`doingText`: the earnings calls of every company come first, then the reading), for how long by the server's own start (`elapsedText`), a meter cut into what was found and what is still to be, and who has passed and who has failed so far. A company being read shows the step it is in in its row of the table (`readingAt`, from `results[].step`: search, relevance, answer, verify); a server that does not say shows "reading…". Why a run failed, and the buttons to try again or clear it, stay in the bar.

The rows are the list that passes the filters, not the answer to a criterion, and three things keep them from reading as one. `stageOf` says where the stage stands in one word for the bar and the output alike, and a run asked for with no criteria is `no_criteria`, never `starting`: a reply once promised the results of a run that did not exist, and the five rows on screen were read as them. When a run finishes, the view sets `state.verdicts` to `['pass']` unless somebody already chose a filter, and an empty table says that a verdict filter hides the rest. `output.qualitative.passed` is the tickers that passed, so the orchestrator reports who passed without opening every company.

Evidence is asked for one company at a time, `{run_id, tickers: [ticker], evidence: true}`, when its row is opened (`state.open`) and again when its answer changes. A criterion's `evidence` is a list of citation ids and `citations` holds each quote once with `id, title, url, quote` (the contract is in screener-mcp's `docs/superpowers/specs/2026-09-20-citations.md`). Quotes stay in a ref, never in state. A citation card shows the title and the quote and opens the server's link with `openLink`; the server has already verified the quote, so the view checks nothing. `usePublishText` publishes the open company's evidence with `[^id]` after every quote, which is how the chat cites it: the terminal resolves the marker against the citations it took from the same tool result.

The orchestrator drives it by state: `place_view { view: 'screener-mcp/screener', state: { filters: [{ field: 'sic_description', op: 'contains', value: 'software' }] } }`, then `set panels/e1/state/filters [...]` with the complete list, and `get panels/e1/output` for what is on screen. The output is kept under the app's 4,096 bytes by `fitOutput`, which gives up tickers at the end of the page first. Point the connection's `url` at another server with the same tools and nothing else in the screener changes.
